## Список фич — источник истины о том, что делать

Файл: `docs/features.json`. Каждая запись — тройка: поведение, команда
верификации, состояние (`not_started` → `active` → `passing`, при провале
`blocked`).

```bash
npm run features next          # какую фичу брать следующей
npm run features start F02     # взять в работу
npm run features verify F02    # запустить верификацию и обновить состояние
```

Правила:

1. **Состояния меняет только скрипт.** Руками `state` в `docs/features.json`
   не правится — статус выставляется по результату запуска команды верификации.
2. **Одна активная фича за раз.** Нельзя начать вторую, не доведя первую.
3. **`passing` необратимо.** Изменилось поведение — заводится новая фича.
4. **`npm run check` перепроверяет все `passing`.** Статус, выставленный без
   реального прохождения верификации, ловится здесь и в CI.
5. **Гранулярность — одна сессия.** «Пользователь может добавить товар в
   корзину» — верно. «Реализовать корзину» — слишком широко. «Создать поле
   name в модели Cart» — слишком узко.

## Определение завершения

Фича завершена = сквозная верификация пройдена и ревью одобрено,
а не «код написан».

| Уровень | Что | Команда | Когда обязателен |
|---|---|---|---|
| 1 | Типы, линт, границы | `npm run check` | всегда |
| 2 | Юнит- и интеграционные тесты | `npm run check` | всегда |
| 3 | Сборка, запуск, критические маршруты | `npm run smoke` | при изменениях на стыке компонентов |
| 4 | Ревью отдельным агентом | `npm run features review` | перед `passing` |

Не переходи к уровню 2, не пройдя уровень 1. Пропущенный обязательный
уровень = не завершено. Ненулевой код возврата = FAIL, дальше идти нельзя.

## Ревью: судит не тот, кто писал

Уровни 1-3 выносит машина — это вердикт кода возврата, его нельзя подделать.
Уровень 4 нужен для того, что машина проверить не может: делает ли код
задуманное, не поехала ли архитектура, можно ли это читать через месяц.

Правила:

1. **Ревью выносит отдельный агент** (`code-reviewer`, `deep-reasoner`, Codex —
   любой со свежим контекстом). Исполнитель себе оценку не ставит: у него
   издержки утопленных затрат и память «я уже решил, что тут нормально».
2. **Контракт вывода фиксирован** — «выглядит хорошо» не принимается.
   Ревьюер обязан дать вердикт по каждому измерению:

   | Измерение | A | B | C | D |
   |---|---|---|---|---|
   | Корректность | все проверки зелёные | основной поток работает | частично | сборка падает |
   | Соответствие замыслу | делает ровно заявленное | мелкие расхождения | заметные расхождения | делает не то |
   | Архитектура | границы соблюдены | мелкие отклонения | явные отклонения | грубые нарушения |
   | Тесты | основной путь + края | только основной путь | каркас | нет |

   Любое `C` и ниже → `rejected` с указанием, что именно чинить.
3. **Вердикт записывается**, иначе его как будто не было:
   `npm run features review F02 approved code-reviewer "что проверено, что найдено"`.
   `npm run check` роняет билд, если passing-фича не имеет одобренного ревью.

## Если в продукте есть LLM

`npm run check` проверяет, что код работает. Он **не** проверяет, что LLM
отвечает хорошо: приложение может быть полностью зелёным и при этом выдавать
плохие ответы. Этот класс регрессий виден только в evals.

Нужны ли они — решается по правилу из `eval/README.md`: если провал нельзя
выразить ассертом (перевод, генерация, извлечение), нужны evals; если можно
(классификация, JSON по схеме), хватит обычного теста в `tests/`.

Когда evals включены:

- прогоняй `npm run eval` **до и после** любой правки промптов и смены модели —
  иначе не отличить улучшение от ухудшения;
- жалоба пользователя на плохой ответ сначала становится кейсом в
  `eval/fixtures/regressions.json`, и только потом чинится;
- эксперимент, который не улучшил score, пиши в `docs/surprises.md` —
  чтобы следующая сессия не повторяла его заново.

## Продвижение обратной связи в правила

Каждая повторяющаяся ошибка, найденная на ревью, превращается в правило
в `scripts/check-boundaries.mjs` — с сообщением WHAT / WHY / FIX. Второй раз
ту же ошибку ловит машина, а не человек. Так harness усиливается сам:
через месяц он строже, чем был, без единого архитектурного решения.

## Чеклист выхода из сессии

- [ ] `npm run check` зелёный
- [ ] `npm run smoke` зелёный, если менялось что-то на стыке компонентов
- [ ] Список фич отражает реальность (`npm run features list`)
- [ ] `PROGRESS.md` обновлён
- [ ] Временные файлы и процессы убраны (порты свободны)
- [ ] `npm run dev` поднимается штатно

Отладочный код (`console.log`, `debugger`) проверяется машинно в `npm run check`.

# nextjs-agent-template

Шаблон Next.js-проекта с запечённой инфраструктурой для работы AI-агентов
(тёплый старт вместо холодного).

## Что внутри

- **AGENTS.md** — входной файл агента: стек, команды, правила, чеклист выхода
  из сессии (+ CLAUDE.md с `@AGENTS.md`)
- **Список фич как примитив** — `docs/features.json` + `scripts/features.mjs`:
  состояние фичи меняется только запуском команды верификации
- **npm run check** — уровни 1-2: типы + линт + тесты + границы + audit фич
- **npm run smoke** — уровень 3: сборка, запуск приложения, критические маршруты
- **Заготовка evals** — `eval/`: score, heatmap ошибок, петля «жалоба → кейс».
  Спит, пока не включишь (`CONFIGURED` в `eval/run-case.mjs`)
- **Гейт ревью** — `passing` невозможен без вердикта отдельного агента
- **Архитектурные границы** — `scripts/check-boundaries.mjs`: правила проекта
  как исполняемые проверки с сообщениями в формате WHAT / WHY / FIX
- **Vitest + Testing Library** — настроены, пример-тест проходит
- **CI** — GitHub Actions гоняет `npm run check` на push и PR
- **PROGRESS.md**, **docs/surprises.md**, **docs/plans/** — состояние между сессиями
- `.env.local.example`, `.nvmrc`, `engines`

## Старт нового проекта

```bash
gh repo create my-app --template bestmark1/nextjs-agent-template --private --clone
cd my-app
npm install
npm run check   # должен быть зелёным до начала работы
```

## Лимит памяти в Docker Compose

Контейнер приложения ограничен по памяти, чтобы утечка или кратковременный
всплеск не вытеснили из RAM соседние проекты на VPS без swap. По умолчанию
`APP_MEMORY_LIMIT=320m`; лимит применяется обычным `docker compose` без
Swarm-режима. Резервирование памяти и ограничение CPU намеренно не заданы.

Чтобы изменить лимит, задайте `APP_MEMORY_LIMIT` в серверном `.env` и
пересоздайте контейнер:

```bash
docker compose -f docker-compose.yml -f docker-compose.production.yml up -d
```

Первая сессия агента: заполнить плейсхолдеры в AGENTS.md, дату в PROGRESS.md,
описать первые фичи в `docs/features.json` — и только потом писать код.

## Почему список фич — примитив, а не документ

Документ агент правит сам, и статус «готово» держится на честном слове.
Здесь состояние меняет только `scripts/features.mjs`, и только когда команда
верификации вернула 0. А `npm run check` (и CI) перезапускает верификацию всех
`passing`-фич — поэтому выставленный без проверки статус становится красным
билдом, а не незамеченной ложью.

```bash
npm run features next          # что делать дальше
npm run features start F02     # взять в работу (одна фича за раз)
npm run features verify F02    # проверить машинно и обновить состояние
npm run features review F02 approved code-reviewer "что проверено"
```

## Кто выносит вердикт

Уровни 1-3 судит машина — код возврата подделать нельзя. Уровень 4 (делает ли
код задуманное, не поехала ли архитектура) машине недоступен, поэтому его
выносит **отдельный агент** со свежим контекстом: исполнитель не оценивает
себя сам. Вердикт записывается в `docs/features.json`, и `npm run check`
роняет билд, если passing-фича осталась без одобренного ревью.

Контракт вывода ревьюера и рубрика A/B/C/D — в AGENTS.md.

## Связь со скиллом phased-engineering-pipeline

Шаблон и скилл — разные слои, они не заменяют друг друга:

- **Шаблон** — инфраструктура репозитория в день первый. Существует всегда.
- **Скилл** — процесс для крупных фич (Narrative → PRD → архитектура → фазы →
  ревью → QA). Вызывается, когда задача того стоит.

Шаблон готовит почву под скилл: `AGENTS.md`, `PROGRESS.md`, `docs/` и
`docs/surprises.md` уже на месте и совпадают с тем, что ожидает пайплайн.
Свои артефакты (`SPEC_PLAN/`, `PROJECT_INDEX.md`, `HANDOFF.md`,
`docs/QUALITY_SCORE.md`) скилл создаёт сам при запуске — держать их пустыми
в шаблоне незачем. Планы фаз из пайплайна ложатся в `docs/plans/`, а их
критерии приёмки — в `docs/features.json` как команды верификации.

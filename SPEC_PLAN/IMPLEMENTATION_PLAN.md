# Implementation Plan — tutu-swipe

**Дата:** 2026-08-04
**Опирается на:** [ARCHITECTURE](ARCHITECTURE.md), [CONSTITUTION](CONSTITUTION.md), [PRD](PRD.md), [план с юнитами U1–U14](../docs/plans/2026-08-04-001-feat-tutu-swipe-discovery-plan.md)

- **Формат отложенного:** запись `Отложено в фазу N: причина` в `HANDOFF.md` и строка в `docs/tech-debt-tracker.md`

## Фаза 1 — Фундамент

**Срок:** до 8 августа · **Юниты плана:** U1, U5, U2

### Цель

Живой вызов MCP с единым бюджетом времени, детерминированный разбор запроса и сквозной проход до перехода на Туту на захардкоженных направлениях.

### Область

Входит: клиент MCP и нормализация ответов в доменные типы, бюджет времени и отмена, фикстуры, разбор запроса правилами, минимальный сквозной сценарий, правила границ в `check-boundaries.mjs`.

Не входит: каталог направлений, веер, снапшот, ранжирование, подборка.

### Файлы

```text
src/lib/mcp/{client,tools,normalize,types}.ts
src/lib/mcp/budget.ts
src/lib/discovery/{parse,schema,dictionaries}.ts
src/lib/packages/build.ts
src/lib/usecases/search-once.ts
src/app/page.tsx
src/app/api/search/route.ts
scripts/check-boundaries.mjs        (дополняется правилами 10, 11, 13)
tests/fixtures/**
tests/{mcp,discovery,packages}/**
```

### Зависимости

Нет. Фаза стартовая.

### Замеры, обязательные к записи в `docs/surprises.md`

- Холодный и тёплый вызов `search_multitransport` и `search_hotels`
- Наличие и характер ограничений по частоте запросов
- Поведение клиента-синглтона при параллельных вызовах
- Фактические лимиты выполнения на Vercel: длительность функции, размер тела запроса, поведение при включённом Fluid Compute

### Definition of Done

- [ ] Вызов MCP из серверного кода возвращает разобранную структуру; типы написаны по фактическим ответам, а не по догадкам
- [ ] Отмена общего сигнала прекращает вызов и не оставляет поздних эффектов
- [ ] Повтор не переживает дедлайн; дедлайн не переживает общий бюджет
- [ ] Разбор запроса правилами даёт одинаковый результат на одной и той же фразе (AC4)
- [ ] Отсутствие города отправления и возрастов детей блокируют поиск с уточняющим шагом (AC2, AC3)
- [ ] Сквозной проход: запрос → три захардкоженных направления → карточки → переход на Туту
- [ ] Итоговая цена — сумма компонентов; цена проживания не умножается на ночи (AC13)
- [ ] Правила границ 10, 11, 13 работают в `check-boundaries.mjs` и ловят нарушение
- [ ] Замеры записаны в `docs/surprises.md`

### Верификация

```bash
npm run check
npx vitest run tests/mcp tests/discovery tests/packages
```

## Фаза 2 — Discovery

**Срок:** до 13 августа · **Юниты плана:** U3, U4 + снапшот

### Цель

Из разобранного запроса — набор направлений, живой веерный поиск по ним с бюджетом времени и потоковой выдачей, плюс предзаготовленный снапшот для мгновенного первого экрана.

### Область

Входит: каталог направлений и офлайн-отбор, скрипт проверки пригодности каталога, скрипт построения снапшота, веер с ограниченной параллельностью и дедлайнами, контракт потока, сборка пакетов.

Не входит: ранжирование, интерфейс ленты, подборка.

### Файлы

```text
data/destinations.json
data/snapshot/**
src/lib/discovery/{catalog,select}.ts
src/lib/search/{fanout,stream,budget}.ts
src/lib/search/snapshot.ts
src/lib/usecases/discover.ts
scripts/validate-catalog.mjs
scripts/build-snapshot.mjs
tests/{discovery,search}/**
```

### Зависимости

Фаза 1: клиент MCP, нормализация, разбор запроса.

### Definition of Done

- [ ] Каталог 40–60 направлений с тегами; `validate-catalog.mjs` прогоняет его через MCP и помечает непригодные
- [ ] Отбор детерминирован, возвращает от 3 до 8 кандидатов, исключает город отправления
- [ ] `build-snapshot.mjs` строит снапшот по каталогу; снапшот лежит в репозитории с датой построения
- [ ] Первое событие потока приходит из снапшота, не дожидаясь MCP (AC7)
- [ ] Живые карточки заменяют снапшотные по мере ответа (AC7a)
- [ ] Контракт потока реализован полностью: `card` с идентификатором события, `candidate_error`, `done`, `aborted`, `unavailable`
- [ ] Три не ответивших направления из восьми не выносят экран (AC9)
- [ ] Полная недоступность MCP даёт `unavailable`, а не пустой `done` (AC10a)
- [ ] Ответ 429 с паузой длиннее дедлайна не повторяется, кандидат помечается не ответившим
- [ ] Поздний прилёт или ранний выезд дают предупреждение на карточке (AC14)

### Верификация

```bash
npm run check
node scripts/validate-catalog.mjs
node scripts/build-snapshot.mjs --dry-run
npx vitest run tests/search
```

## Фаза 3 — Обучение и интерфейс

**Срок:** до 18 августа · **Юниты плана:** U13, U6, U7, U14, U8

### Цель

Лента свайпа с реакциями, подписанное клиентское состояние, ранжировщик за общим интерфейсом с измеренной базовой линией и объяснения.

### Область

Входит: подпись и проверка состояния, пересчёт модели из журнала, лента и её состояния, реакции с причинами, две реализации ранжировщика, протокол воспроизведения, объяснения.

Не входит: подборка, переход на Туту, сквозные сценарии отказов.

### Файлы

```text
src/lib/session/{state,serialize,sign}.ts
src/lib/ranking/{interface,features,bayesian,rules,diversity,replay}.ts
src/lib/explain/{aggregate,phrases}.ts
src/lib/usecases/react.ts
src/app/swipe/[sessionId]/page.tsx
src/app/api/react/route.ts
docs/ranking-baseline.md
tests/{session,ranking,explain}/**
tests/fixtures/sessions/**
```

### Зависимости

Фаза 2: поток, пакеты, снапшот.

### Definition of Done

- [ ] Состояние от клиента без действительной подписи отвергается
- [ ] Состояние ранжировщика пересчитывается из журнала; подменённые веса не влияют на выдачу
- [ ] Порог доступности подборки считается из длины проверенного журнала и не поддаётся подделке счётчика (сама подборка — фаза 4)
- [ ] Повторная реакция с тем же идентификатором засчитывается один раз (AC23)
- [ ] Обрыв потока восстанавливается с последнего события; перезагрузка восстанавливает журнал, позицию и состояние (AC11)
- [ ] Реакция доступна свайпом и нажатием; отмена откатывает реакцию, модель и позицию (AC22, AC24)
- [ ] Причины дизлайка влияют на выдачу: город исключается, два подряд запускают дозабор, цена и время двигают веса (AC19, AC20)
- [ ] Правило разнообразия соблюдается на любом окне из пяти карточек (AC21)
- [ ] Одинаковая установка генератора и одинаковые реакции дают идентичную ленту (AC25)
- [ ] Обе реализации ранжировщика проходят общий контрактный набор
- [ ] `docs/ranking-baseline.md` получен **до 15 августа**; по нему принято решение о точке отсечения
- [ ] Объяснение не показывается при недостатке подтверждений и не ссылается на отсутствующие признаки (AC26, AC27)

### Верификация

```bash
npm run check
npm run smoke
npx vitest run tests/session tests/ranking tests/explain
```

## Фаза 4 — Завершение

**Срок:** хакатон, 19–20 августа · **Юниты плана:** U9, U10, U11, U12

### Формат сдачи (уточнён 2026-08-06)

Очного питча не будет. Сдаются: исходники, короткое видео запуска, README и развёрнутое приложение по публичной ссылке.

### План деплоя (решено 2026-08-06)

Разворачиваем на своём VPS `185.79.138.118` (Ubuntu 20.04, 2 ГБ RAM, 2 ядра, Docker 28.1.1).

Там уже стоит **Traefik v3.1** на 80/443 с автоматическими сертификатами Let's Encrypt и сетью `web_gateway`. Рядом работают восемь контейнеров чужих проектов — их не трогаем.

- **Схема размещения:** по образцу `/opt/apps/_template-compose` — базовый compose плюс production-вариант, приложение приватно и выходит только через Traefik. Каталог `/opt/apps/tutu-swipe`
- **Домен:** `tutu-swipe.185.79.138.118.nip.io` — работает без настройки DNS, сертификат выдаётся автоматически
- **Сборка образа:** локально, на сервер передаётся готовый. На сервере 452 МБ свободной памяти и нет swap: сборка на месте рискует уронить чужие контейнеры
- **Требуется от приложения:** сборка Next.js в standalone-режиме и маршрут `/health` — его ждёт healthcheck из шаблона
- **Деплой выполняется только с отдельного разрешения владельца** — это публикация

Отсюда приоритеты фазы: документация и читаемость репозитория весят больше, чем репетиция живого выступления — жюри изучает проект без автора. Детерминированный режим с фиксированным seed нужен не для страховки на сцене, а чтобы дубль видео воспроизводился при пересъёмке.

### Цель

Подборка по ссылке, переход на Туту для всех типов продуктов, устойчивость развёрнутого приложения, документация, видео и деплой.

### Область

Входит: кодирование подборки во фрагмент, страница подборки с пересборкой, переход по всем типам, сквозные сценарии отказов, репетиция, README и схема архитектуры.

### Файлы

```text

src/app/list/page.tsx
src/lib/mcp/checkout.ts
src/app/api/checkout/route.ts
README.md

tests/{link,e2e}/**
```

### Зависимости

Фаза 3 полностью.

### Definition of Done

- [ ] Подборка кодируется во фрагмент URL; параметры не попадают в серверные логи (AC33a)
- [ ] Ссылка открывается на другом устройстве без сессии (AC32)
- [ ] Испорченная или несовместимая ссылка даёт понятную страницу (AC33)
- [ ] Исчезнувшее предложение заменяется с пометкой (AC33b)
- [ ] Длина ссылки для трёх поездок проверена тестом
- [ ] Надпись перехода соответствует типу, который вернул MCP (AC34)
- [ ] Состав пассажиров передаётся полностью (AC35)

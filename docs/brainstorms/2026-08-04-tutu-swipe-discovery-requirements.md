# Требования: discovery-механика для Туту (хакатон 2026)

**Дата:** 2026-08-04
**Статус:** требования согласованы, готово к планированию
**Формат участия:** соло + агентский стек (Claude Code, Codex, Qwen)
**Ревизия:** v2 — после критического ревью (Codex, 2026-08-04)

## Контекст

ИИ-хакатон Туту на их MCP-сервере (`https://mcp.tutu.ru/mcp`).

- Регистрация до **14 августа**, хакатон **19–20 августа**, результаты **21 августа**
- До 5 человек в команде, до 30 команд
- Призы: 75 000 / 50 000 / 25 000 ₽ + мерч
- Сдаём: исходники + презентация, 10 минут питча

**Оценка (100 баллов):** UX/UI — 20, Функциональность — 15, Соответствие теме — 10, Инновационность — 10, Документация — 10, Стабильность — 10, Архитектура — 10, Качество кода — 10, Презентация — 5.

**Двойная цель.** Организаторы прямо заявили о формировании кадрового резерва и готовности «реализовать вместе интересные проекты». Решение оценивают не только как демо, но и как показатель того, каково с автором работать. Документация и внедряемость — часть продукта.

**Асимметрия по времени.** Большинство команд собирают проект за два дня хакатона. Работа начинается 4 августа — ~15 дней подготовки. Всё, что требует времени (слой генерации кандидатов, обучение на лайках, вылизанный UI), — зона отрыва.

## Проблема

Тревел-поиск работает, когда пользователь знает, куда едет. Когда не знает — он уходит из сервиса: в телеграм-каналы с подборками, в Пинтерест, к друзьям. Возвращается уже с готовым названием города, и сервис получает только транзакцию, теряя весь этап выбора.

Формулировка «хочу на море в сентябре, вдвоём из Москвы, тысяч за шестьдесят, чтобы не шумно» не превращается в поисковый запрос ни в одном тревел-сервисе. Здесь discovery и ломается.

## Продуктовая форма

Свайп-подбор поездок, который обучается на реакциях внутри сессии.

1. **Свободный запрос.** Одно поле, из которого извлекаются: **город отправления** (обязателен — без него нет ни цены, ни времени в пути; если не назван, спрашиваем отдельным шагом), состав путешественников, окно дат, бюджет, вайб. Бюджет трактуется как сумма на всю поездку и на всю группу; валюта — рубли. Нечёткие даты («в сентябре») сводятся к **одному конкретному окну выезда** до запуска поиска — иначе комбинаторика взрывается.
2. **Отбор кандидатов в два этапа.** Сначала дешёвый офлайн-отбор по каталогу направлений (без обращений к MCP), затем веерный поиск только по прошедшим отбор.
3. **Свайп по карточкам поездок.** Карточка — поездка целиком: дорога туда-обратно + жильё + итоговая цена.
4. **Реакция с причиной.** Лайк — одной кнопкой. Дизлайк — с быстрым выбором причины: дорого / долго добираться / не тот город / не тот отель. Причина снимает главную неоднозначность сигнала и одновременно даёт материал для объяснений.
5. **Перестройка выдачи.** После каждой реакции переранжируется уже собранный пул; новый веерный поиск запускается только при исчерпании пула или при явном сигнале «не тот город» по нескольким карточкам.
6. **Шорт-лист.** Доступен с 5-й реакции, финализируется на 10-й. Содержит до 3 вариантов, живёт по постоянной ссылке и открывается на чужом устройстве.
7. **Checkout.** Из шорт-листа — переход на Туту через `create_checkout_link`.

### Что такое «готовая поездка»

Пакет собирается из независимых результатов поиска, поэтому целостность обеспечивается явными правилами, а не подразумевается:

- Отель ищется на даты, выведенные из выбранного транспорта (прибытие → заселение, выезд → отправление обратно)
- Если прибытие позже 22:00 или выезд раньше 8:00, пакет помечается предупреждением, а не отбрасывается молча
- Обратная дорога ищется тем же вызовом, что и прямая, состав пассажиров одинаков во всех компонентах
- Итоговая цена — сумма компонентов; на карточке показывается разбивка, чтобы число не выглядело магией

### Почему свайп, но не «тиндер на двоих»

Свайп берётся сознательно: он попадает в вкус жюри (судья публично назвал тиндер-механику) и бьёт в самый весомый критерий — UX/UI.

Синхронный свайп вдвоём с двух устройств **отклонён**: муж и жена и так обсуждают поездку между собой, отдельный синхронный ритуал добавляет шаг, а не ценность. Социальный эффект достигается дешевле — шерингом готового шорт-листа в тот же чат, где спор и так идёт.

### Риск копирования и чем он снимается

Судья назвал тиндер-механику в публичном анонсе — свайп сделают ещё 5–8 команд. Отрыв дают три вещи, которых у двухдневных проектов не будет:

- **Слой discovery** — генерация направлений из свободного запроса (в MCP этого нет)
- **Обучение на реакциях с причинами** и честные объяснения выдачи
- **Полная воронка до корзины** — большинство остановится на красивой выдаче

## Что даёт и чего не даёт MCP

Проверено обращением к живому серверу `tutu-mcp-server 0.29.1` (2026-08-04).

**Есть:**

| Инструмент | Что даёт |
|---|---|
| `search_avia` / `search_rail` / `search_bus` / `search_etrain` | Поиск по видам транспорта, фильтры `price_max`, `direct_only`, `carriers`, сортировки |
| `search_multitransport` | Один вызов — все виды транспорта параллельно, `optimize_for: price\|time` |
| `search_hotels` | Отели по городу и датам; фильтры по звёздам, рейтингу, удобствам, питанию, бесплатной отмене |
| `get_offer_details` | Фото, удобства, политика отмены, отзывы с текстами и темами (`review_topics`) |
| `get_rail_seatmap` | Карта вагона по местам |
| `create_checkout_link` | Deeplink в корзину пользователя (сервер корзину не создаёт) |
| `fetch_resource` | Ресурсы `tutu://geo`, `tutu://amenities/dictionary`, `tutu://special-offers` |

**Нет — и это определяет архитектуру:** ни один инструмент не умеет discovery. Все `search_*` требуют явный `destination`. Запрос «покажи, куда поехать» не существует на уровне API.

Отсюда главный технический блок: **слой генерации кандидатов**. Это и есть часть, которую за два дня не пишут.

**Ограничения, которые надо держать в голове:**

- Сервер read-only, платежей и бронирований нет
- Правило грунтования: нельзя выдумывать поля, которых нет в ответе
- Цена отеля (`price_basis="stay_total"`) — уже итог за все ночи, умножать на `stay.nights` нельзя
- Города-омонимы: `meta.from` / `meta.to` / `meta.resolved_geo` возвращают разрезолвленное, `also_named[]` сигналит о неоднозначности
- Авиа round-trip с пересадками не деплинкуется — падает в поиск; состав пассажиров нужно прокидывать в `create_checkout_link`, иначе корзина откроется на одного взрослого

### Как честно называть воронку

Формулировка «доводим до корзины» некорректна: сервер корзину не создаёт, а часть авиаофферов ведёт только в результаты поиска. Точная формулировка, которую используем и в продукте, и на питче: **«переход на Туту с максимально предзаполненным состоянием, какое поддерживает конкретный оффер»**. Тип перехода (`kind`) возвращается самим MCP — его и показываем пользователю честно: либо «открыть корзину», либо «выбрать места», либо «открыть подборку на Туту».

### Цены

Карточка не обещает совпадение с итогом на Туту. Цена помечается временем поиска, при переходе показывается предупреждение, что стоимость могла измениться. Расхождение из-за состава пассажиров считается багом: состав прокидывается во все вызовы и в `create_checkout_link`.

## Рекомендательная механика

**Данных для обучения нет ни у кого из участников.** Заявление «мы обучили модель» на защите означает обучение на выдуманных данных, и техническое жюри увидит это первым же вопросом. Строим то, что честно работает без обучающей выборки, и **не переоцениваем возможности 10–15 наблюдений**.

**Модель.** Логистическая регрессия онлайн-обновлением на **малом наборе плотных признаков** (порядка 8–10): цена относительно бюджета, время в пути, число пересадок, вид транспорта, звёзды, рейтинг отеля, 2–3 агрегированные темы отзывов, признак «море/город/горы». Разреженные и внутрисессионно-постоянные признаки (сезонность, конкретный отель) исключены сознательно — на 15 наблюдениях они дают шум, а не сигнал.

**Разведка.** Thompson sampling поверх коэффициентов с широким prior, плюс жёсткое правило разнообразия: среди любых 5 подряд карточек не больше 2 из одного города. Без него выдача схлопывается после пяти свайпов.

**Причины дизлайка** входят в обновление напрямую: «дорого» двигает вес цены, «не тот город» исключает город из пула, «долго добираться» двигает вес времени в пути. Это компенсирует малый объём наблюдений — один явный сигнал стоит нескольких неявных.

**Объяснимость — отдельный детерминированный слой**, а не вывод коэффициентов модели. Считается по агрегатам реакций: «три из четырёх лайков — прямые рейсы», «два дизлайка по цене выше 70к». Формулировка собирается по шаблонам из этих агрегатов, показывается только при достаточном числе подтверждений и не зависит от случайности сэмплирования.

**Как доказать, что рексис работает.** Метрика — не «выдача изменилась», а сравнение с базовой линией: доля лайков во второй половине сессии против первой, и против контрольного прогона со статическим ранжированием по цене. Замеряется заранее на своих прогонах, цифра идёт на слайд.

## Производительность и отказоустойчивость

Это не строка в рисках, а требование первого класса — от него зависят и UX/UI, и стабильность, и то, увидит ли жюри живой MCP.

- **Двухэтапный отбор.** Каталог направлений отфильтровывается офлайн (сезон, тип локации, ориентировочная досягаемость из города отправления) до 6–8 кандидатов. Отбрасывание непригодного города после полного веерного поиска — слишком поздно.
- **Бюджет времени.** Первая карточка показывается не позже 3 секунд после запроса. Достигается progressive rendering: пул наполняется по мере ответов, интерфейс не ждёт завершения веера.
- **Ограничение параллельности** на вызовы MCP, дедлайн на кандидата, отмена хвостовых запросов после набора достаточного пула.
- **Частичный отказ — норма.** Если часть городов не ответила, показываем то, что есть, и дозагружаем. Ошибка MCP не должна выносить экран.
- **Retry с backoff** на сетевые ошибки, размыкание после повторных отказов конкретного домена.
- **Кэш** с ключом по (город отправления, город назначения, окно дат, состав) и коротким TTL; возраст цены хранится и показывается.
- **Детали карточки** (`get_offer_details`: фото, отзывы) грузятся лениво, после показа карточки, и никогда не блокируют первый экран.

## Хранилище

Шорт-лист открывается по ссылке на чужом устройстве — значит состояние **персистентное**, а не в памяти процесса. SQLite-файл (или управляемый KV, если деплой окажется serverless) с записями сессии и шорт-листа, доступ по идентификатору в ссылке. Модель bandit живёт в сессии и не переживает её — это осознанно.

## Живые данные и тесты

Два разных вопроса, которые нельзя смешивать:

- **Продукт работает только на живом MCP.** Никаких зашитых выдач.
- **Тесты работают на записанных контрактных фикстурах.** Сборка пакета, расчёт итоговой цены, обработка частичных отказов и омонимов проверяются детерминированно. Это требование к качеству кода, а не отступление от «живых данных».
- **Резервный прогон демо** — страховка на случай падения сети в зале, а не режим работы. Если он включается, это проговаривается жюри вслух.

## Критерии успеха

1. Свободный запрос на естественном языке превращается в набор реальных поездок с ценами из живого MCP
2. Первая карточка на экране не позже 3 секунд после отправки запроса
3. Доля лайков во второй половине сессии выше, чем в первой, и выше контрольного прогона со статическим ранжированием — цифра измерена и вынесена на слайд
4. Каждая карточка при достаточном числе реакций объясняет своё присутствие в терминах прошлых реакций пользователя
5. Сценарий проходится до конца: запрос → реакции → шорт-лист → ссылка открывается на другом устройстве → переход на Туту
6. Падение или таймаут части вызовов MCP не выносит экран
7. Репозиторий читается человеком из Туту как код, с которым можно работать дальше

## Границы

**Не входит:**

- Синхронный свайп с нескольких устройств — отклонён продуктово
- Аккаунты, авторизация, история пользователя между сессиями
- Оплата и бронирование — MCP их не поддерживает
- Обучение на исторических данных — данных нет
- Мобильное приложение — мобильный веб покрывает сценарий

**Отложено:**

- Брендированные подборки под спецпроекты маркетинга — на питче упоминается как продолжение
- Голосовое управление фильтрами

## Порядок сборки и точки отсечения

Скоуп полный, но с явными точками отсечения: если этап не закрыт к своей дате, следующий начинается всё равно, а хвост уходит в отложенное. Это страховка от сценария, где не успевается сразу UX, стабильность и документация — то есть 40 баллов из 100.

| # | Этап | Готово к | Что отсекаем при просрочке |
|---|---|---|---|
| 1 | Сквозной срез: захардкоженный запрос → 3 города → живой MCP → простые карточки → ссылка на Туту | 7 августа | Ничего, это фундамент |
| 2 | Каталог направлений + офлайн-отбор + веерный поиск + сборка пакетов | 12 августа | Каталог сокращается до 30 городов |
| 3 | Реакции с причинами, модель, разнообразие, слой объяснений | 15 августа | Модель упрощается до взвешенных правил без Thompson sampling |
| 4 | UX: анимации, фото и отзывы, мобильный вид, состояния загрузки и пустоты, undo, tap-альтернатива свайпу | 18 августа | Анимации, но не состояния — состояния обязательны |
| 5 | Шорт-лист и шеринг | хакатон, день 1 | — |
| 6 | Устойчивость, README, схема архитектуры, замер метрики, сценарий демо | хакатон, день 2 | — |

К 14 августа (дедлайн регистрации) этапы 1–2 должны быть закрыты: к моменту регистрации механика собирается на реальных данных.

## Требования к демо

10 минут питча не выдержат 15 живых свайпов плюс ожидание веера. Поэтому:

- **Детерминированный режим демо**: фиксированный seed для сэмплирования, чтобы прогон воспроизводился
- Заранее отрепетированный сценарий на 6–8 свайпов, где перестройка выдачи видна
- Метрика из критерия 3 показывается графиком, а не «доверьтесь»
- Сравнение «с обучением / без обучения» бок о бок — единственный способ сделать невидимый рексис видимым для нетехнического жюри

## Допущения и риски

| Риск | Как снимаем |
|---|---|
| Веерный поиск не укладывается в 3 секунды до первой карточки | Двухэтапный отбор, progressive rendering, дедлайны, кэш — заложены в требования, замеряются на этапе 2 |
| MCP нестабилен во время защиты | Частичный отказ как норма, retry с backoff, кэш последнего успешного ответа, резервная запись с оговоркой вслух |
| Кандидат оказался без транспорта или жилья | Офлайн-отбор до веера + отбрасывание пустых результатов |
| Модель на 15 наблюдениях не показывает эффекта | Малый набор плотных признаков, причины дизлайка как сильный сигнал, замер против базовой линии заранее; при провале — откат к взвешенным правилам (этап 3) |
| Свайп-механику делают ещё 5–8 команд | Отрыв в discovery-слое, объяснимости и полной воронке |
| Тем из `review_topics` не хватает как признаков | Проверяется на этапе 2 на реальных ответах; при нехватке — признаки только по структурным полям |

**Допущения, требующие проверки на реальных прогонах (этап 2):**

- Веерный поиск по 6–8 городам укладывается в бюджет времени
- `review_topics` даёт устойчивые темы, пригодные как признаки
- `tutu://special-offers` (помечен экспериментальным) даёт полезный сигнал для отбора кандидатов — до проверки на него не закладываемся

## Решения по ранее открытым вопросам

- **Источник каталога направлений:** гибрид. Заготовленный каталог 40–60 городов с тегами (собирается заранее и прогоняется на пригодность через MCP), поверх — отбор под конкретный запрос. Чистая генерация LLM отвергнута: непредсказуема по времени и даёт города без предложений.
- **Число реакций до шорт-листа:** шорт-лист доступен с 5-й, финализируется на 10-й. Фиксированный порог вместо «пока модель не уверена» — на таком объёме наблюдений уверенность модели не является надёжным сигналом.
- **Форма объяснения:** одна строка на карточке, показывается только при достаточном числе подтверждающих реакций. Не показывать объяснение лучше, чем показать выдуманное.

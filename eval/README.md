# Evals — контур качества LLM-выхода

Тесты проверяют, что код работает. Evals проверяют, что **LLM отвечает хорошо**.
Это разные вещи: приложение может пройти весь `npm run check` и при этом
переводить плохо.

## Нужны ли они этому проекту

Не всякий вызов LLM требует evals. Правило:

| Ситуация | Что нужно |
|---|---|
| Выход LLM **и есть ценность** продукта: перевод, генерация текста, извлечение данных. Правильного ответа нет, качество размытое | **Evals.** Только они покажут, стало лучше или хуже после правки промпта |
| LLM — компонент с **проверяемым контрактом**: классифицировать в одну из пяти категорий, вернуть JSON по схеме, выбрать маршрут | Обычные тесты в `tests/`. Scored-eval здесь будет ритуалом |

Короткая формулировка: **если провал нельзя выразить ассертом — нужны evals.
Если можно — нужен тест.**

Пока `CONFIGURED = false` в `run-case.mjs`, `npm run eval` пропускает прогон
и выходит с 0. Ничего удалять не нужно.

## Как включить

1. В `eval/run-case.mjs` поставь `CONFIGURED = true` и реализуй `runCase`
2. Заполни `eval/fixtures/cases.json`, убрав плейсхолдеры
3. `npm run eval`

Eval не входит в `npm run check`: он стоит денег и требует ключей провайдера.
Прогоняется вручную — **обязательно** перед правкой промптов, сменой модели
и деплоем изменений, затрагивающих выход LLM.

## Два цикла улучшения

**Цикл А — эксперименты с архитектурой.** Меняешь одно: промпт, модель,
провайдера, разбиение на шаги. Прогоняешь eval. Лучше — оставляешь, хуже —
откатываешь и пишешь в `docs/surprises.md`, чтобы следующая сессия не
повторяла тот же эксперимент.

**Цикл Б — реальные провалы в набор.** Пользователь пожаловался на плохой
ответ — кейс сначала попадает в `fixtures/regressions.json`, и только потом
чинится. Иначе через месяц никто не вспомнит, что именно было сломано,
и регрессия вернётся незамеченной.

Цикл Б важнее цикла А: придуманные за столом кейсы всегда легче реальных.
Набор из тридцати живых провалов ценнее двухсот сочинённых.

## Размер набора

Двенадцать кейсов не отличают 85% от 95% — одна фраза двигает метрику на
восемь пунктов. Это шум, а не сигнал. Порог имеет смысл, когда кейсов
хотя бы несколько десятков и они покрывают разные категории (поле `tag` —
по нему строится heatmap, показывающий, что чинить первым).
